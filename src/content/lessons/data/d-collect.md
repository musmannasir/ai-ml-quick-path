## In plain words
Most company data lives in **databases**, and **SQL** is the language for asking them questions. `SELECT` picks columns, `WHERE` filters rows, `JOIN` connects tables (customers with their orders), and `GROUP BY` summarises (orders per customer). Data also comes from logs, files, sensors, forms and public datasets. Before using any data, check that you are **allowed** to (owner, licence, customer consent, privacy rules) and that it **represents** the people and situations the model will meet. **Labelling** means adding the right answer to examples, usually by people following a written guide. People disagree, so you measure **agreement**: if two careful labellers often disagree, the task or the guide is unclear, and no model will learn it well.

```diagram compare What the main SQL words do

- `SELECT` | Picks columns
- `WHERE` | Filters rows
## Connect and summarise | model
- `JOIN` | Connects tables, such as customers with their orders
- `GROUP BY` | Summarises, such as orders per customer
```

## Real-world example
A support team wants to auto-sort tickets into "bug", "billing" and "other". Two agents label the same 200 tickets. They agree 82.5% of the time, but mostly disagree on billing questions about bugs. They add three examples of those to the guide, re-label, and agreement rises. Better labels improved the final model more than any algorithm change.

```diagram loop The labelling improvement in the support team
- Two agents label 200 tickets | The same tickets | input
- Compare | They agree 82.5% of the time | process
- Find the disagreements | Mostly billing questions about bugs | warn
- Add three examples to the guide | Then re-label | output
loop: Re-label and measure agreement again
```

## How it works
1. Write the question and list the data you need.
2. Find the source; record owner, permission and date range.
3. Pull data with SQL into a table with one row per example.
4. Write a labelling guide with definitions and tricky examples.
5. Have two people label a sample; compute agreement; fix the guide.
6. Label the rest; spot-check quality.

```diagram flow From question to labelled data
- Question and data list | What you need | input
- Source and permission | Owner, permission, date range | warn
- SQL pull | One row per example | store
- Labelling guide | Definitions and tricky examples | process
- Two people label a sample | Compute agreement, fix the guide | process
- Label the rest | Spot-check quality | output
```

### Related concepts
- **Active learning**: let the current model pick the examples it is least sure about and send only those to human labellers. You reach good accuracy with far fewer labels.
- **Weak supervision**: create approximate labels with rules, keyword lists or existing systems, then train on them; useful when hand-labelling is too slow. Check quality on a small hand-labelled set.
- **Synthetic data**: generated data (by scripts, simulators or LLMs) used for practice, testing or to cover rare cases. It is how every example in this guide avoids real personal data. It can miss real-world quirks, so always validate on real data before production.
- **Data augmentation**: creating extra training examples by changing existing ones (flip or crop an image, reword a sentence).

```diagram compare Four ways to get more or cheaper labelled data
## Fewer labels needed | model
- Active learning | The model picks the examples it is least sure about for humans to label
- Data augmentation | Change existing examples: flip or crop an image, reword a sentence
## Labels or data made by machines | process
- Weak supervision | Approximate labels from rules, keyword lists or existing systems
- Synthetic data | Generated by scripts, simulators or LLMs; validate on real data
```

## .NET (C#) example
Query SQL Server (or any database) with `Microsoft.Data.SqlClient` and parameters, and build the feature rows:
```cs Program.cs
using Microsoft.Data.SqlClient;

const string sql = """
    SELECT c.Id, COUNT(o.Id) AS NOrders, COALESCE(AVG(o.Amount), 0) AS AvgAmount
    FROM Customers c LEFT JOIN Orders o ON o.CustomerId = c.Id
    WHERE c.Country = @country
    GROUP BY c.Id
    """;
using var connection = new SqlConnection(Environment.GetEnvironmentVariable("SALES_DB"));
await connection.OpenAsync();
using var command = new SqlCommand(sql, connection);
command.Parameters.AddWithValue("@country", "UK");          // never paste user input into SQL text
using var reader = await command.ExecuteReaderAsync();
var rows = new List<CustomerFeatures>();
while (await reader.ReadAsync())
    rows.Add(new CustomerFeatures(reader.GetInt32(0), reader.GetInt32(1), Convert.ToSingle(reader.GetValue(2))));
Console.WriteLine($"{rows.Count} customers loaded");

public record CustomerFeatures(int Id, int NOrders, float AvgAmount);
```

## Applied Maths - Statistics
Short, optional reading. Open a topic to see the formula, what it means and worked examples. The numbers are small, made-up values chosen so you can check them by hand.

### Average and count per group (what GROUP BY computes)
**Where it is used:** the SQL query that gives each customer's number of orders and average order amount.

```formula Count and average
count   = number of rows in the group
average = sum of the values ÷ count
```
**In plain words:** GROUP BY makes one small pile per customer. COUNT counts the pile and AVG adds it up and divides by the count.

**Example 1: customer with orders.** Customer 3 has two orders, 80 and 120. Count = 2. Sum = 80 + 120 = 200. Average = 200 ÷ 2 = 100.

**Example 2: customer with no orders.** Customer 4 has no orders. Count = 0, and the average would be 0 ÷ 0, which is undefined, so SQL returns NULL. The LEFT JOIN keeps this customer, and COALESCE(AVG(...), 0) turns the NULL into 0. Without the LEFT JOIN the customer would be missing from the result.

### Cohen's kappa (agreement beyond luck)
**Where it is used:** checking whether two labellers follow the labelling guide the same way.

```formula Cohen's kappa
kappa = (po - pe) ÷ (1 - pe)
po = share of items where both labellers agree
pe = share of agreement expected by luck
     = sum over labels of (share A gives that label × share B gives that label)
```
**In plain words:** raw agreement can look high just by luck. Kappa removes the lucky part. 1 is perfect agreement and 0 is no better than luck.

**Example 1: balanced labels.** Two labellers agree on 85 of 100 items, so po = 0.85. Both say "spam" half the time and "ok" half the time. pe = 0.5 × 0.5 + 0.5 × 0.5 = 0.50. kappa = (0.85 − 0.50) ÷ (1 − 0.50) = 0.35 ÷ 0.50 = 0.70.

**Example 2: rare label.** Both say "ok" 90% of the time and "spam" 10%, and they agree on 90 of 100 items, so po = 0.90. pe = 0.9 × 0.9 + 0.1 × 0.1 = 0.81 + 0.01 = 0.82. kappa = (0.90 − 0.82) ÷ (1 − 0.82) = 0.08 ÷ 0.18 = 0.44. The same 90% raw agreement is only moderate once luck is removed.

## Common mistakes
- Using an inner `JOIN` and silently losing customers with no orders.

```diagram compare Inner JOIN and LEFT JOIN
note: Same customers and orders tables, different result.
## Inner JOIN | bad
- Customers with orders | Kept
- Customers with no orders | Silently lost
## LEFT JOIN | output
- Customers with orders | Kept
- Customers with no orders | Kept, with a count of 0
```
- Building SQL by pasting text from users, which allows SQL injection. Use parameters.

```diagram compare Pasted text or a parameter
## Pasting user text into SQL | bad
- Result | The text can run as SQL code: SQL injection
## Using a parameter | output
- Result | The database treats the value as data, never as SQL code
```
- Labelling without a written guide, so each person uses different rules.
- Collecting personal data you are not allowed to use for this purpose.

## Quick check
Q: Why use a LEFT JOIN to build a customer feature table?
A: It keeps every customer, including those with no orders, instead of dropping them.

Q: What does a low agreement score between labellers tell you?
A: The task or the labelling guide is unclear, so labels are noisy and a model will struggle to learn them.

Q: Why use query parameters?
A: The database treats parameter values as data, never as SQL code, which prevents SQL injection.
